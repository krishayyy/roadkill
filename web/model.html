System architecture

From five state DOT crash files to an on-device risk score.

Five stages, each with a documented failure mode it was built to avoid: a clustering algorithm tuned against a real DBSCAN percolation, a label leak caught and fixed with spatial cross-validation, and a runtime fusion rule that guarantees bad weather can never make the app less cautious.

Every stage below is what the scripts and Swift source in this repo actually do — no step here is aspirational.

Stage 1 → 2

Clustering that's tuned against its own failure mode, not a textbook default

The standard approach — DBSCAN with an eps chosen from the "k-distance knee" — was implemented first, measured, and rejected. On Iowa's real 85,366-point dataset, the textbook knee picks eps ≈ 2,593 m. At that radius, DBSCAN percolates: crash points chain together along the continuous road network into one county-spanning mega-cluster, not a set of actionable corridors.

The real percolation sweep (Iowa)

v3 instead sweeps a density-adaptive grid of candidate eps values and takes the largest one that does not percolate — no cluster holding more than 5% of the state's points. This is that actual sweep, from cluster_tuning_v3.json.

What that means concretely

Rejected: textbook knee—
Chosen: percolation-bounded—

At the knee's ~2,593 m, this same curve sits between 34% and 65% of all Iowa points collapsing into a single cluster — a county, not a corridor. The chosen 899 m keeps every cluster under the 5% ceiling while still capturing real spatial agglomeration.

Clusters are shaped further into road-segment polylines (PCA principal axis + equal-count binned vertices), not flat circles — but only when points are genuinely road-shaped (elongation ≥ 2.5×, buffer tighter than the plain-circle radius). Otherwise the script ships a circle and says why the polyline was rejected, rather than faking precision.
Stage 3

The leak: a crash record helping build the corridor that then predicted it

Two of the model's fifteen features — distance_to_nearest_corridor_m and corridor_base_severity — come from the DBSCAN clusters above. The earlier pipeline built those clusters from every positive row, including the ones later used to test the model. A crash helped create the very corridor whose distance was then fed back in as a predictor of that same crash. Reported ROC AUC: 0.867.

The fix: spatial block cross-validation

One fold of StratifiedGroupKFold over ~22 km geographic blocks. A held-out block's corridor features are rebuilt from training-fold data only — its own neighborhood contributes nothing to the corridors it's scored against.

The honest result

The exported model is fit on out-of-fold corridor features specifically — not full-data ones — so the leak can't get baked into the model's learned weights, only into the (now-corrected) metric.

Leaky (v2, reported)0.867 ROC AUC
Leaky, reproduced exactly on v3 data0.853–0.860
Honest — spatial block CV0.8205 ROC AUC

A lower honest number is the correct outcome of fixing a leak, not a regression — confirmed by reproducing the exact leaky setup on the same states and getting back close to the original 0.867. See the Data page for the per-state breakdown.

Stage 4

Export: the model card travels with the model

The trained GradientBoostingClassifier (150 estimators, depth 3) converts directly to CoreML via coremltools, with the same 15-feature schema and order the Swift side expects — no field mapping to keep in sync by hand. Its honest metrics, the leaky comparison, and every known limitation are written into the .mlpackage's own short_description, so the model documents itself wherever it's inspected, not just in this repo.

🔒 Staged, not live

Exports to WildlifeRiskModel_v3.mlpackage, never overwriting the shipping model — swapping the live model is a deliberate, separate, human-performed step.

🧾 Self-documenting

Version string: 3.0-real-multistate-leakage-fixed-ia-il-va-ma-tn. The honest ROC AUC, the leaky comparison, and the states used are embedded in the model file itself.

📴 Fully on-device

No network or LLM call happens at inference time — WildlifeRiskModel.prediction(input:) runs locally, so the risk score works with no connectivity.

Stage 5

Runtime fusion: why weather is applied last, once, to the whole blend

The model learned something real but dangerous to use directly: it predicts lower collision probability for fog, rain, and snow than for clear weather — not because bad weather is safer, but because the overwhelming majority of driving (and of the crash records it trained on) happens in clear conditions, so raw frequency swamps per-mile risk. Feeding it live weather made the app's own score go down in fog.

Applying the weather multiplier once, last, to the combined blend — rather than feeding real weather into the ML model — is what keeps the two systems from contradicting each other.
